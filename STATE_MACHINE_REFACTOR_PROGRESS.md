## N01 design investigation (not implemented)

The current whole-metadata ETag is `"r-<sum>"`; because old source revisions are stored as signed SQLite integers and the resource sums multiple sources, reserving an unproven numeric range cannot guarantee disjointness from all previously issued validators. A forward migration therefore needs an explicitly versioned metadata ETag namespace, with legacy metadata validators rejected as stale, plus a durable per-item generation retained across withdrawal/recreation. Every source-document insertion, update, deletion and owner transfer, and every scanned-origin insertion, title change, deletion or transfer that affects the projection, must advance the affected generation in the same transaction. Item deletion/recreation and overflow need explicit handling; a deleted generation must not silently be reused. The metadata response schema requires a decimal numeric revision, so that field remains the per-history generation and can rewind after restore; the metadata ETag is the history-bound concurrency validator. Other resources' ETags remain unchanged. The implementation below is not yet verified end to end.
